## The failure path, also live (before the fix, same door)

The first leg run hit a REAL provider outage and exercised the contract's
most important clause — *failure can never read as success* (02 §6):

```
+0.0 s  capture_raw                 human
+0.9 s  agent_invoke_started        clio   timeout_s 180
+181 s  agent_invoke_result         clio   outcome timeout · 180255 ms
+181 s  capture_triaged_failure     clio   reason: timeout — nothing landed
```

The chokepoint held its own 180 s cap exactly; the failure event is
append-only beside the raw capture; no task/question/loop/note row was
minted; the capture stays in the list as `failed` with its retry
affordance. A dying provider is a legal terminal, not a silent note.

## The infra outage the leg found (root cause)

clio's model (`glm/glm-5.3-flash` via 9Router) was returning **429 code
1113 "Insufficient balance or no resource package. Please recharge"**
from the GLM upstream; hermes schedules its retry at 180 s, colliding
exactly with the triage timeout — so every agent call timed out. The
key, the router, and the network were all healthy (44 models in 41 ms);
the GLM provider's balance was not.

**Fix applied 2026-11-19 00:20 IST**: clio's `model.default` switched to
`ds/deepseek-chat` in `~/.hermes/profiles/clio/config.yaml` (same
provider, key and router; the previous config kept as
`config.yaml.bak-20261119`). clio answers a trivial prompt in ~11 s.
Note: every other clio-ridden flow (digest, debrief, weekly review) was
almost certainly stalling on the same balance death — this switch
revives them too.
